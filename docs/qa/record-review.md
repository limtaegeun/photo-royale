## 테스트 환경과 사전조건

- 호스트 1명, 참가자 2명 이상(A/B 팀), 진행 중 방 1개.
- 기록 데이터: 현재 라운드 pending 1건, approved 1건, rejected 1건, 이전 라운드 pending 1건 이상.
- 브라우저: 데스크톱 Chrome CDP + 모바일 뷰포트 320×568, 390×844, 430×932.
- 실제 Firebase 데이터 생성은 계정·방·participants·submissions 문서를 남기는 side effect이며, 생성 즉시 manifest에 계정/uid/방 코드/문서 ID를 기록한다.
- 실기기 iOS Safari/Android Chrome, 화면 잠금 5분+, 60분 체류는 자동화 범위 밖이면 `⏸ 미검증`으로 남긴다.
- 기록 200건 초과 절단(D-05)은 실 데이터로 재현하기 비현실적이므로 서버 query shape 단위 검증으로 충분하며, live-qa 스팟 재현은 생략한다.

## 알려진 한계

1. 기록 사진은 Firestore 문서 data URL이며, 서버에서 `createdAt` 내림차순 + `limit(RECORD_LOG_LIMIT=200)`으로 최근 200건만 구독한다(이전엔 전체 컬렉션 무제한 구독 — 2026-07-26 finding). 200건을 초과하는 오래된 기록은 화면에 절단 사실을 알리지 않고 조용히 제외된다. 페이지네이션·"더 보기"는 이번 변경 범위가 아니다.
2. (해소됨) 게임이 waiting 상태여도 기록 탭은 playing일 때와 동일하게 지난 라운드 기록을 보여준다 — 대기실의 `지난 라운드 기록 보기`도 이 상태로 들어온다(과거: 시작 전 안내로 대체되어 2026-07-26 finding으로 지적됨). 판정 탭은 여전히 playing 게이트를 유지한다(판정 쓰기는 rules가 playing에서만 허용).
3. terminal Listen 오류는 자동 재구독하지 않고 새로고침을 복구 절차로 안내한다.
4. iOS Safari/Android Chrome, 화면 잠금 5분+, 60분 체류는 실기기 증거 없이는 통과 처리하지 않는다.
5. `?tab=log` 쿼리는 마운트 시 1회만 읽는다. `activeTab`은 이후 로컬 상태로만 동작해 탭을 전환해도 URL 쿼리는 동기화되지 않는다 — 운영 탭으로 옮긴 뒤 새로고침하면 마지막 URL(예: `?tab=log`)이 다시 기록 탭을 연다.
6. 같은 차수 재실행 가드(`roundPlayMarker`, `sessionStorage` 기반)는 이 기기·이 탭에서만 유효하다. 새 탭·다른 기기·시크릿 모드·저장소 삭제 시 마커가 없어 가드가 발동하지 않고 같은 차수가 확인 없이 재시작된다. 서버(rules) 강제는 후속 과제 — 소비측(대기실 다이얼로그) 상세는 `waiting-room.md` 알려진 한계 참조.
