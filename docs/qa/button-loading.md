- **브랜치**: `main` 작업 트리 (미커밋 변경 — 커밋 전 검증)
- **작성일**: 2026-07-25
- **컨텍스트**: 오프라인 이벤트(야외 실기기 진행)용 — **이벤트 당일 장애 허용 불가**. 이번 변경은 UI 피드백 계층이지만 **방 생성·초대 코드 입장·레디**라는 당일 크리티컬 경로의 CTA를 직접 건드리므로, 표시 검증 + 해당 경로 회귀를 함께 다룬다.

## 코드에서 도출한 크리티컬 리스크 (중점 검증 근거)

1. **로딩 중 버튼이 disabled 색으로 전환된다**: `BaseButton`은 `loading`을 네이티브 `disabled` 속성으로 처리하고(`isBlocked`), 클래스에 `disabled:bg-disabled disabled:text-content-disabled`가 걸려 있다. 스피너는 `border-current`로 그 색을 상속한다 → **진행 중 주 CTA가 브랜드색을 잃고 회색 + 회색 스피너**가 된다. 코드 주석상 의도된 설계("variant/disabled 색 자동 반영")지만, 야외 직사광 실기기에서 스피너가 식별 가능한지는 실측이 필요하다 (F-01, F-02).
2. **스크린리더 상태 고지가 약해졌다**: 이전에는 라벨 자체가 `로그인 중…`으로 바뀌어 읽혔지만, 지금은 `aria-busy="true"`만 남고 라벨은 `invisible`(DOM 유지)이다. `role="status"` 라이브 리전은 없다 → 진행 상황이 음성으로 announce되지 않을 수 있다 (F-05).
3. **입장 화면 제출 상태가 ref → computed로 바뀌었다**: `isSubmitting`은 이제 파생값이라 대입이 불가하다. 상태 전이는 전부 `pendingAction`으로만 일어나므로, 전이 누락 시 **버튼이 영구 로딩/영구 비활성**으로 굳는다. 특히 실패 경로(`catch`)와 조기 return(빈 코드)에서의 해제를 실측한다 (C-04, C-05, C-07).
4. **빠른 응답 시 스피너 플래시**: 로컬·고속망에서 응답이 100ms 내에 끝나면 스피너가 번쩍이고 사라진다. 기능 결함은 아니지만 체감 품질 항목으로 기록한다 (F-06).
5. **초대 코드 입력창은 여전히 `isSubmitting` 기준으로 잠긴다**: 두 CTA 중 어느 것이 진행 중이든 입력창이 disabled 된다 — 방 만들기 중에도 코드 입력이 잠기는 것이 의도인지 확인 (C-06).
6. **라벨 기반 자동화·QA 절차 영향**: 로딩 중에도 버튼 텍스트가 불변이라, "텍스트로 진행 상태를 판별"하던 기존 QA 절차·자동화는 `data-loading`/`aria-busy` 기준으로 바뀌어야 한다 (기존 `waiting-room.md` A-04 기대값 갱신 대상).

## 테스트 환경·사전 조건

- 로컬 dev: `npm run dev` (Firebase env `.env.local` 필요 — Auth/Firestore 실연결)
- baseline 대조: 배포 환경 `https://photo-royale-scc.web.app` — **주의**: 직전 배포에 이번 변경이 포함되지 않았으므로 배포 환경이 곧 "수정 전(before)" 이다. 텍스트 교체 방식과 스피너 방식을 같은 조작으로 나란히 비교할 수 있다.
- **계정**: ① 호스트 A, ② 게스트 B, ③ 신규 가입용 미사용 이메일 1개(B군), ④ 잘못된 비밀번호 조합(A군 실패 경로)
- **기기 매트릭스**: 데스크톱 Chrome(주 검증) + iOS Safari 또는 Android Chrome 실기기 1대 이상(F군 시인성·터치)
- 네트워크 시뮬레이션: DevTools Slow 3G / Fast 3G 스로틀(스피너 관측 시간 확보에 필수 — 로컬은 너무 빨라 F-06 외에는 스로틀 없이 관측 불가), 오프라인 토글(실패 경로)
- 모션 설정: OS `prefers-reduced-motion` on/off 전환 수단(macOS 손쉬운 사용 → 동작 줄이기)
- 접근성: VoiceOver(macOS/iOS) 또는 Chrome 접근성 트리 패널
- 표기: **[unit]** = 단위 테스트가 이미 커버 → live-qa에서는 통합 관점 재확인만, 무표기 = live-qa 중점 대상
- 판정 공통 기준: 로딩 상태의 증거는 버튼 텍스트가 아니라 **`data-loading="true"` + `aria-busy="true"` + 스피너 렌더 + 클릭 차단** 4종이다.

## 알려진 한계 (버그 아님 — 오탐 방지)

1. **로딩 중 버튼이 회색(disabled 톤)으로 보이는 것은 현 `BaseButton` 설계다** — `loading`을 네이티브 `disabled`로 처리하고 스피너가 `currentColor`를 상속하기 때문. 개선 여부는 F-01/F-02 실측 결과로 판단할 사항이며, 그 자체를 버그로 보고하지 않는다.
2. **로딩 중 라벨 텍스트가 바뀌지 않는 것이 이번 변경의 의도다** — `로그인 중…`이 보이지 않는 것은 정상. 진행 상태는 `data-loading`/`aria-busy`/스피너로 판정한다.
3. **`ProfilePage`의 `로그아웃` 버튼에는 로딩 표시가 없다** — 진행 상태 플래그가 스토어에 없어 이번 범위에서 제외했다(미구현이지 회귀가 아님).
4. **`대기실에 입장하는 중…`(WaitingRoomPage), `카메라 권한을 확인하는 중…`(CameraPage)은 버튼이 아니라 화면 상태 문구(`role="status"`)로 그대로 남아 있다** — 스피너 전환 대상이 아니었다.
5. **`.firebase/` 디렉터리가 untracked로 남아 있다** — 직전 배포 캐시이며 앱 동작과 무관.
6. **`waiting-room.md` A-04의 기대값("제출 중 버튼 disabled — isSubmitting")은 이번 변경으로 "누른 CTA 스피너 + 반대 CTA disabled"로 바뀐다** — 해당 문서 갱신 전까지 옛 기대값을 기준으로 오탐하지 않는다.
