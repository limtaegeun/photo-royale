## 코드에서 도출한 크리티컬 리스크

1. 방·참가자·공지 `onSnapshot`의 영구 오류는 한 번 안내한 뒤 입장 화면으로 안전하게 이동한다. (H-01)
2. 카메라는 HTTPS/localhost와 사용자 권한이 필수이며 iOS/Android의 후면 카메라 선택 결과가 다를 수 있다. (A-02, H-02)
3. 생존 탈락 데이터 모델이 아직 없어 `N팀 생존`은 이번 차수에 배정된 고유 팀 수를 표시한다. (B-03)
4. 킬샷은 브라우저 메모리의 Blob URL만 만들며 기기 갤러리 저장·호스트 전송은 의도적으로 하지 않는다. (E-02, F-01)
5. 상·하단 HUD가 작은 화면/큰 글자에서 뷰파인더를 과도하게 가릴 수 있다. (G-01, G-02)
6. `BaseButton`의 패딩·배경은 사용처 클래스 덮어쓰기가 아닌 `padding` prop과 `shutter` variant로 선택한다. (J-01, J-02)

## 테스트 환경·사전 조건

- local: 현재 워크트리 Vite dev 서버, 실제 Firebase 프로젝트
- baseline: `main`은 HUD 이전 상태이므로 기능 대조가 필요한 대표 케이스만 사용
- 계정: 호스트 1명, 참가자 2명 이상. 참가자는 같은/다른 팀 조합 포함
- 방 상태: `status=playing`, `assignmentRound>=1`, `round.status=running`
- 브라우저: 데스크톱 Chrome fake camera + iOS Safari/Android Chrome 실기기 후속 확인
- 카메라 자동화: Chrome `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream`
- 네트워크: Firestore Listen/Write 응답과 DOM을 함께 판정. 콘솔 직접 수정은 rules를 우회하므로 rules 근거로 사용하지 않음

### 조건부 애니메이션 최종 재검증

- 실제 overflow를 `scrollWidth > clientWidth`로 판정한다. 짧은 공지는 정적으로 표시하고 넘치는 공지만 초과 거리만큼 좌우로 애니메이션한다.
- 390×844 실제 Firebase 긴 공지에서 가용 폭 `277.5px`, 본문 `scrollWidth 694.5px`, 이동 거리 `417px`, `notice-marquee` 활성화를 확인했다.
- 애니메이션 시작부와 끝부분 모두 펼치기 아이콘은 오른쪽 끝에 고정되고 페이지 가로 폭은 390px를 유지했다.
- 펼침 후 `animation: none`, 가용 폭 `277.5px`, 전체 URL 줄바꿈을 확인했다. 짧은 공지 대조군은 새 백엔드 데이터를 만들지 않고 단위 테스트에서 `scrollWidth 100px < clientWidth 240px`로 검증했다.
- 읽기 속도 조정: 이동 속도를 약 `24px/s`로 낮추고 양 끝 10% 구간을 정지시켰다. `alternate`를 제거해 마지막 문구 도달 후 다음 반복은 첫 문구에서 다시 시작한다. 390px 실측에서 2.5초 약 60px, 5초 약 123px 이동했다.
- 펼친 상태의 내부 행은 `items-start`로 전환되어 왼쪽 `공지` 헤더와 오른쪽 펼침 아이콘이 여러 줄 본문의 상단에 고정된다.
