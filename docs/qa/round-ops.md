## 2. 코드에서 도출한 크리티컬 리스크

| # | 리스크 | 근거(코드) | 담당 TC |
|---|---|---|---|
| **R-1** | **🔴 rules 미배포 시 운영 전면 마비** — `round` 갈래와 `notices` 갈래가 **둘 다 신규**다. 구버전 ruleset에서는 라운드 시작·정지·공지가 **전부 403**이고, 화면은 에러 토스트만 반복한다. 1차 QA에서 같은 사고(배정 확정 403) 전례 | `firestore.rules:32-47, 118-124, 190-210` | F-01·F-11, P0-04, 체크리스트 0 |
| **R-2** | **구독 에러 콜백 없음** — `subscribeToRoom`/`subscribeToParticipants`/`subscribeToLatestNotice` 모두 `onSnapshot(query, onNext)` 형태로 **error 핸들러가 없다**. 권한 상실·세션 만료 시 화면이 **조용히 갱신 중단**되고, 첫 스냅샷 전에 실패하면 `phase`가 `loading`에 머물러 `라운드 상태를 불러오는 중…`이 영구 표시된다 | `rooms.ts:242`, `notices.ts:56` | O-01, O-04 |
| **R-3** | **남은 시간은 뷰어 기기 시계로 계산** — 앵커(`startedAt`)만 서버 시각이고 `computeRemainingMs`는 `Date.now()`를 쓴다. 호스트 폰 시계가 5분 틀리면 **호스트가 보는 남은 시간 자체가 5분 어긋난다**(참가자 화면은 아직 없어 대조 불가) | `useRoundTimer.ts:26-34` | M-04 |
| **R-4** | **serverTimestamp 지연 보상** — 쓰기 직후 로컬 스냅샷의 `startedAt`은 null이고, 이때 `computeRemainingMs`는 경과를 0으로 본다(= 총량 그대로 표시). 온라인에서는 수백 ms 뒤 정정되지만, **오프라인에서는 서버 확정 전까지 타이머가 멈춘 것처럼 보인다** | `rooms.ts:118`, `useRoundTimer.ts:32` | M-02 |
| **R-5** | **일시정지 값은 클릭 순간의 클라 계산값** — `pauseRound(code, computeRemainingMs(round, Date.now()))`. 네트워크가 느리면 실제 반영까지의 지연만큼 참가자 기준 남은 시간이 늘어난다(스펙상 허용, 크기 실측 필요) | `useRoundOpsStore.ts:158-160` | A-11, M-01 |
| **R-6** | **시간 조정 대기값은 창별 로컬 상태** — `pendingAdjustMinutes`는 Pinia 로컬. 호스트가 두 창을 열면 각 창이 별도 대기값을 갖고, 각각 반영하면 **합산 적용**된다 | `useRoundOpsStore.ts:50` | B-09, N-02 |
| **R-7** | **토스트 뷰포트 전역 변경** — 하단 여백을 96px로 올렸다. round-ops 탭 바는 해소되지만 **모든 화면의 토스트 위치가 바뀐다**(대기실·입장·프로필·배정 보드) | `BaseToastProvider.vue:17-19` | H-04, I-04 |
| **R-8** | **하단 탭 sticky 전환** — `sticky bottom-0` + `bg-canvas`. 스크롤 중 카드가 탭 뒤로 지나갈 때 배경 비침·겹침, 그리고 safe-area 적용 위치(탭 바가 직접 보유)가 실기기에서만 검증 가능 | `RoundOpsPage.vue:111, 236` | G-04, H-05 |
| **R-9** | **종료는 서버에 남지 않는다** — remaining ≤ 0은 클라이언트 판정이고 문서에는 여전히 `status: 'running'`이다. 뷰어마다 시계가 다르면 종료 시점이 갈릴 수 있고, 새로고침해도 '종료'는 재계산으로만 성립한다 | `useRoundTimer.ts:70` | A-07, A-08 |
| **R-10** | **게스트 가드가 대기실로 되돌릴 때 재입장이 일어난다** — `waiting` 방에서 게스트를 `/waiting-room/{code}`로 replace하면 대기실 `enter()`가 다시 돈다(멱등이라 레디는 보존되어야 한다) | `RoundOpsPage.vue:76-83` | D-02 |
| **R-11** | **공지 길이 계산 이중 기준** — 화면 카운터·`maxlength`는 JS UTF-16 길이, rules `size()`는 유니코드 문자 수. 이모지 입력 시 카운터가 실제보다 크게 셈(전송은 통과) | `NoticeSheet.vue:48-53` vs `firestore.rules:206` | C-07 |
| **R-12** | **`isActionPending`은 라운드 쓰기만 가드** — 공지 전송은 별도 플래그(`isSendingNotice`)라 **라운드 조작과 공지 전송이 동시에 나갈 수 있다**. 서로 다른 문서라 충돌은 없으나 오프라인 큐 순서 확인 필요 | `useRoundOpsStore.ts:104-110, 214` | N-03 |

## 15. 알려진 한계 (버그가 아닌 현 스펙 — 오탐 방지)

1. **종료 후 재시작해도 라운드 번호는 그대로다.** 다음 라운드 재배정 플로우는 별도 작업(계획 §8).
2. **게스트 화면에는 타이머·공지 수신 UI가 없다.** 데이터(`round`·`notices`)는 게스트가 그대로 구독하면 되도록 설계됐지만 카메라 콕핏 UI는 후속.
3. **판정/기록 탭은 준비 중 안내만**. 판정 대기 건수·판정 플로우는 보류 확정(계획 §8).
4. **게임 종료(playing → waiting)는 앱에서 불가** — rules 단방향. 콘솔에서만 되돌린다.
5. **시간 조정 대기값은 창별 로컬 상태**(R-6) — 호스트 창을 2개 열면 각각 쌓인다.
6. **하단 탭 항목 높이 40px** — `BaseSegmented` 기존 스펙.
7. **뒤로가기로 대기실에 돌아갈 수 없다** — `replace` 스펙.
8. **공지 글자 수 카운터는 JS 문자열 길이 기준** — 이모지 1개를 2로 센다(rules는 문자 수 기준이라 전송은 통과).
9. **남은 시간은 뷰어 기기 시계로 계산된다**(앵커만 서버 시각) — 기기 시계가 틀리면 그만큼 어긋난다(M-04).
10. **종료 상태는 서버에 기록되지 않는다** — `round.status`는 계속 `running`이고 클라이언트가 0 도달을 종료로 표시한다.

### ℹ️ 알려진 한계로 문서화할 실측 거동 (버그 아님)

- **오프라인에서 라운드 시작/재개 시 타이머가 멈춰 보인다** — 서버 앵커(`startedAt`) 확정 전에는 경과가 0으로 계산된다. 실측: 오프라인 재개 후 6초 동안 `10:00` 고정 → 온라인 복귀 즉시 `09:57`로 정정(R-4 예측대로).
- **오프라인 쓰기 중에는 모든 라운드 컨트롤이 잠긴다** — `isActionPending`이 서버 ack까지 유지되어 일시정지·재개·반영이 전부 disabled. 온라인 복귀 시 자동 해제(영구 잠김 아님).
- **기기 시계 오차가 그대로 표시된다** — `Date.now`를 +5분으로 조작하니 남은 시간이 정확히 5분 적게 표시(`15:24 → 10:23`). 앵커만 서버 시각이라는 설계의 알려진 대가(한계 9).
- **손상된 라운드 상태는 클라이언트 권한으로 만들 수 없다** — `round` 필드 삭제·`status:'bogus'` 모두 rules가 403으로 거부(A-12·E-06이 ⏸인 이유). 방어가 의도대로 동작한다는 뜻.

### ⏸ 미검증 8건과 사유

| TC | 사유 |
|---|---|
| A-12, E-06, E-07 | 손상 상태·문서 삭제를 만들 수단이 없다(클라 rules 403, admin ADC 미설정). 단위 테스트가 `toRoundState`의 null 수렴을 커버 |
| D-09 | 뒤로가기 — 1차 QA D-02에서 ✅ 확인된 `replace` 스펙, 이번 회차 미재검증 |
| H-05, M-06 | iOS/Android **실기기** 필요(safe-area·실제 터치) |

| M-07 | 카카오톡 인앱 브라우저 — 실기기 필요 |

### ⚠️ 부분 검증 3건

- **C-06**: 키보드 입력 경로는 `maxlength`로 정상 차단(30자 타이핑 = 30자) — 초과 경로만 위 발견 3.
- **E-05**: 배정 데이터 변경 후 요약이 `13팀 배정`으로 정확히 집계됨은 확인했으나, **구독을 통한 라이브 갱신**(새로고침 없이)은 분리 검증하지 못했다.
- **G-02**: 이번 라운드 배정자만 집계하는 로직은 단위 테스트(`useRoundOpsStore.spec`)가 커버. 실데이터에서 **직전 라운드 잔재가 섞인 상태**는 만들지 못했다(playing 방에서는 재배정이 rules로 막힌다).

## 19. 당일 운영 체크리스트 (round-ops)

0. **🔴 배포 순서**: `firestore.rules`를 앱과 **함께** 배포한다. 이번 변경은 `round` 갈래와 `notices` 갈래가 신규라, 미배포 시 **라운드 시작·정지·시간 반영·공지가 전부 403**이다. 1차 QA에서 같은 유형의 사고가 실제로 있었다(배정 확정 403).
1. **시작 전 스모크(P0-04)**: 테스트 방에서 `라운드 시작` 1회 + 공지 1건 성공 확인. 하나라도 실패하면 **이벤트 시작 보류**.
2. **호스트 폰 시계 확인(M-04)**: 자동 시각 동기화 ON. 남은 시간은 호스트 기기 시계로 계산된다.
3. **새로고침·기기 교체 대비(P0-03)**: 타이머 정본이 서버라 호스트 폰이 죽어도 다른 기기로 재로그인하면 이어받는다. 백업 기기 1대와 호스트 계정 크리덴셜을 현장에 확보.
4. **되돌리기 한계**: 게임 자체를 `waiting`으로 되돌리는 것은 앱에서 불가(콘솔 필요). 라운드 타이머는 `라운드 시작`으로 언제든 20분 재설정 가능.
5. **참가자 안내**: 게스트 화면에는 아직 타이머·공지가 뜨지 않는다. 남은 시간·공지는 **구두 전달**이 필요하다(한계 2).
6. **HTTPS 전제**: 게스트 카메라 권한은 보안 컨텍스트에서만 동작.
