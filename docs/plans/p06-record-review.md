## 1. 배경 — 기획서의 "라운드"가 무엇인지 확정한 것이 이 브랜치의 출발점

작업 도중 "라운드가 모드마다 여러 번 도는 건지, 라운드마다 모드가 바뀌는 건지"가 불명확해 기획서를 다시 읽고 결론을 냈다. **이 해석이 B 작업의 근거 전부**이므로 여기 남긴다.

### 결론: 라운드 = 게임 모드 1개를 담는 슬롯

기획서 §1 소요 시간 타임테이블이 결정적이다.

```
1차 팀편성 10분 → 1차 게임 준비 5분 → 1차 게임 20분
2차 팀편성 10분 → 2차 게임 준비 5분 → 2차 게임 20분
3차 팀편성 10분 → 3차 게임 준비 5분 → 3차 게임 20분
```

**"팀편성 → 준비 → 게임" 세트가 통째로 반복**된다. 여기서 두 가지가 읽힌다.

1. **게임 슬롯이 고정 개수**이고 각 20분이다 — 한 모드를 여러 슬롯에 걸쳐 늘려 하는 구조가 아니다.
2. **라운드마다 팀편성을 처음부터 다시 한다** — 모드가 안 바뀐다면 편성을 3번 다시 할 이유가 없다. §3의 모드들은 **요구하는 편성 단위가 서로 다르기 때문**이다.

| 모드 | 요구 편성 |
|---|---|
| 일반전 (§3.1) | 2인 1조 팀, 각 팀 개별 경쟁 |
| 꼬리잡기 (§3.2) | 알파벳 상성 체인 (A→B→C…) |
| 그룹전 (§3.3) / 왕잡기 (§3.4) | 완장 색 4그룹 연합 |
| 스태프 추격전 (§3.5) | 전원 동맹 vs 스태프 |
| 폭탄설치전 (§3.6) | 공격그룹 / 수비그룹 |
| 꼼꼬미 (§3.7) | 전체의 10% 술래 지정 |

편성이 모드에 종속되므로 "편성 + 게임"이 한 쌍으로 반복된다. 또 타임테이블이 모드명을 지정하지 않고 **"1차/2차/3차 게임"이라고만 쓴 것** 자체가, 모드는 상수가 아니라 **운영 중 진행자가 고르는 변수**라는 뜻이다.

### 모드 내부 반복은 꼼꼬미(§3.7) 하나뿐

§3.7에만 *"종료 및 라운드 재개"* 절이 있고 다음 술래 선정 규칙까지 명문화돼 있다. 나머지 모드에는 없다 — **부재가 곧 스펙**이다. 즉 "한 모드를 여러 라운드에 걸쳐 이어 한다"는 경로는 꼼꼬미를 빼면 존재하지 않는다.

> ⚠️ 기획서가 "라운드"를 두 층위로 쓴다. **① 외부 차수**(타임테이블 1차/2차/3차 = 코드의 `assignmentRound`)와 **② 모드 내부 판**(꼼꼬미의 술래 교대, 왕잡기 §3.4의 "즉시 라운드 패배"). 코드에는 ①만 있다.

| 4 | 총 소요 시간 초과 | **감수한다.** 5모드면 245분(4시간 5분)으로 기획서 3시간을 65분 초과하지만 시간을 줄이지 않는다 |

### 5번 보충 — 다시 제안하지 말 것

의도한 진행 순서는 일반전 → 꼬리잡기 → 그룹전 → 왕잡기 → 스태프 추격전이지만, **그 순서를 코드에 표로 고정하는 안은 사용자가 폐기했다.** 모드는 라운드마다 진행자가 배정 보드에서 고르는 값으로 유지하고, `GameModePicker`도 그대로 둔다.

> §3.1~3.5가 한 덩어리인 이유: 제외된 §3.6(폭탄설치전)·§3.7(꼼꼬미)·§3.8(빠른생존)은 **전부 QR 스캔이 필수**다. 3.1~3.5는 카메라 + GM 판정만으로 성립한다. 즉 이 범위는 QR 인프라 없는 MVP 경계와 정확히 일치한다.

## 3. 작업 A — 라운드 운영 기록 탭

`RoundOpsPage`의 세 번째 탭이 "준비 중" 카드로 비어 있던 것을 채웠다.

### 데이터

`rooms/{code}/submissions` 컬렉션을 **전 라운드·전 상태로** 구독한다(판정 큐는 `status == 'pending'` + 현재 라운드만 보는 별개 구독).

```ts
interface SubmissionRecord extends Submission {
  targetTeam: string | null  // 확정(approved) 시 잡힌 팀 완장, 대기·반려는 null
  judgedAtMs: number | null  // 판정 시각, 대기 중이면 null
}
```

- **게으른 구독**: 사진이 data URL이라 무겁다 → enter에서 항상 열지 않고 **기록 탭이 처음 활성화될 때** `watchRecordLog()`가 시작한다(스토어가 중복 시작을 막는다).
- **정렬은 클라이언트**: 복합 인덱스를 피하려고 라운드 내림차순 → 라운드 안에서는 최신 제출 순으로 클라이언트에서 정렬한다.

### 화면

| 상황 | 동작 |
|---|---|
| 이번 라운드의 대기 건 | 행을 누르면 **판정 시트**가 열려 그 자리에서 판정 |
| 판정 완료 / 지난 라운드 대기 건 | **읽기 전용 상세 시트**로 사진 확대 확인 |

지난 라운드 판정은 `firestore.rules`가 막으므로 판정 시트를 열어줘도 실패한다 — 그래서 애초에 열지 않는다.

**추가 파일**: `components/RecordLogList.vue`, `components/RecordDetailSheet.vue`, `recordStatusStyles.ts`, `api/submissions.ts`(`subscribeToSubmissionLog`), `stores/useRoundOpsStore.ts`(`watchRecordLog`)

## 4. 작업 B — 라운드 종료 처리 ⭐ 이 브랜치의 핵심

### 문제

타이머가 0에 닿으면 **'라운드 시작' 버튼이 다시 나왔다.** 그런데 `startRound()`는 `round` 필드만 쓰고 **`assignmentRound`를 올리지 않는다.** 결과적으로 "2라운드"가 아니라 **같은 편성·같은 완장·같은 라운드 번호로 20분이 덧붙는** 동작이었다.

여기서 두 가지가 깨진다.

1. **미판정 킬샷이 새 20분에 섞인다.** 판정 게이트가 `record.round === assignmentRound`인데 라운드 번호가 그대로라, 직전 20분의 미판정 건이 새 타이머의 판정 큐에 계속 남는다.
2. **기록이 뭉갱친다.** 제출물이 `round`로만 구분되니 40분치가 1라운드로 집계된다.

여기에 확정 스펙 2번(5모드 전부 진행)을 더하면, 한 모드가 슬롯을 2개 먹는 순간 5모드를 돌릴 수 없다.

### 해결

**종료 상태(`isRoundEnded`)의 주 액션을 '라운드 시작' → '라운드 종료'로 교체**했다. 쓰기는 기존 `endGame()`과 동일하다(방을 `waiting`으로 되돌리고 `round` 삭제). **새 데이터 모델도 rules 변경도 필요 없었다** — 배관이 이미 다 있었기 때문이다.

```
타이머 0 → [라운드 종료] → status=waiting, round 삭제 (assignmentRound는 보존)
                          → 대기실 복귀
                          → "N+1차 팀 배정" CTA 노출 → 거기서 다음 모드 선택
```

세부 결정 3가지:

| 결정 | 이유 |
|---|---|
| 종료 상태에서 '게임 종료' 버튼을 **감춘다** | '라운드 종료'와 **쓰기가 완전히 동일**하다. 같은 일을 하는 버튼이 둘 보이면 진행자가 차이를 찾느라 멈춘다 |
| 미판정 킬샷이 남았을 때**만** 확인 다이얼로그 | 종료는 중단이 아니라 타임테이블대로의 다음 단계다. 다만 종료 후엔 rules가 지난 라운드 판정을 막아 **되돌릴 수 없으므로** 남은 건수를 밝힌다 |
| '먼저 판정하기'는 **판정 탭까지 데려간다** | 닫기만 하면 라벨이 약속한 동작과 어긋난다 (live-qa에서 발견해 수정) |

## 5. 작업 C — 대기실 차수·게임 모드 표시 (미커밋)

### 문제

대기실 기본 화면에 **모드가 아예 없었다.** `room.gameMode`는 게스트가 배정받은 뒤 보는 카드에만 넘어갔다. 모드를 보려면 배정 편집 화면까지 들어가야 하는데, 그 화면에 들어가면 대기실이 사라진다.

작업 B 이후 이게 더 중요해졌다. 라운드를 종료하면 진행자가 **바로 이 화면으로 돌아오는데**, 버튼이 둘이다.

- **게임 시작** → 직전 차수·직전 모드를 **그대로 다시** 실행
- **N+1차 팀 배정** → 새로 편성하고 새 모드 선택

배정 보드의 모드 기본값이 "직전 라운드 모드"라, 진행자가 안 바꾸면 조용히 같은 모드가 반복된다. 화면에 표시가 없으면 '게임 시작'이 무슨 모드를 켜는지 알 수 없다.

### 해결

룸 카드에 한 줄을 추가했다. 새 카드도, 새 데이터도 필요 없다.

```
┌─────────────────────────────────┐
│  ROOM 4NYY            [대기 중] │
│  4차 라운드 · 왕잡기            │  ← 추가
│  ┌───────────────────────────┐  │
│  │      초대 링크 복사       │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

- **`assignmentRound > 0`일 때만 렌더한다.** `normalizeRoom`이 `gameMode` 없는 방을 기본값 `'normal'`로 채우므로, 배정 전에도 값은 '일반전'으로 읽힌다 — 그대로 보여주면 **진행자가 고르지도 않은 모드를 확정된 것처럼 알리게 된다.**
- **차수를 모드와 붙여 쓴다.** 하단 CTA가 "N+1차 팀 배정"이라, 카드가 "4차 · 왕잡기"라고 해야 두 버튼의 차이가 읽힌다.
- **이 줄을 보는 건 호스트와 "이번 라운드에 배정되지 않은 게스트"다.** 배정된 게스트는 룸 카드가 `RoundAssignmentCard`로 통째 대체되어 보지 못하고, 그쪽 규칙서가 모드명을 이미 보여준다(live-qa W-03 실측).

**10개 케이스 전부 통과.** [QA 보고서(스크린샷 12장 포함)](https://claude.ai/code/artifact/ae9f056a-c42e-435a-b23d-589a1a0b8762) · `docs/qa/round-finish-report.html`

```
[재시작 전] assignmentRound=1  submissions=[{status:"pending", round:"1"}]
[재시작 후] assignmentRound=1  submissions=[{status:"pending", round:"1"}]
            durationMs=1200000  ← 새 20분이 걸렸는데 차수가 그대로 → 미판정 건이 새 큐에 남음
```

QA 중 발견해 고친 것 2건: ① 게스트 시야에 대한 코드 주석이 사실과 달랐음 ② '먼저 판정하기'가 판정 탭으로 가지 않았음. 개선 후보 1건(다이얼로그에서 파괴적 액션의 색 무게가 안전 액션보다 강함)은 디자인 결정이라 남겨뒀다.

## 7. 남은 작업 · 미정 스펙

### 다음 작업 (별도 진행하기로 함)

**§3.2~3.5 네 모드 실제 구현** — 현재 `available: true`는 `normal` 하나뿐이라 다른 모드를 고를 수 없다.

1. `game-mode/modes/`의 `available` 플래그 열기
2. **모드별 편성 알고리즘 확장** — 지금 배정은 2인 1조만 된다. 꼬리잡기는 알파벳 상성 체인, 그룹전·왕잡기는 4색 그룹, 스태프 추격전은 전원 동맹이라 편성 단위 자체가 다르다. `game-mode/types.ts` 주석이 이미 이걸 후속 작업으로 적어뒀다.

이쪽이 라운드 종료 배선보다 훨씬 큰 작업이다.

### 기획 미정 (기획자 확인 필요)

| 항목 | 내용 |
|---|---|
| **라운드별 점수 누적** | 3~5라운드에 걸친 최종 순위 산정 규칙이 기획서 어디에도 없다. 모드마다 점수 단위가 달라(일반전 팀 점수 +30 / 왕잡기 그룹 감점 / 스태프 추격전 생존 비율 / 빠른생존 포인트 적립) 어떻게 하나로 합칠지 미정 |
