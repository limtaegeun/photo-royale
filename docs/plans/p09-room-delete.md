# P09 방 삭제 — 진행자가 지난 방을 지운다

- **작성일**: 2026-11-03 (사용자 구두 요구: "방 삭제 할 수 있도록 하고, 삭제 전에 해당 내용 알려 주면서 진짜 삭제할 거냐고 묻는 확인 모달을 띄우고 진행")
- **기준 코드**: main `ec077a1`
- **화면 문구**: 규칙서·기획서에 없는 기능이라 아래 §3 문구는 개발이 지었다. **기획 확인 필요.**

## 0. 한 줄 요약

입장 화면의 `내가 만든 방` 시트에서 방마다 삭제 버튼을 누르면, 그 방에 쌓인 것(참가자·킬샷 사진·라운드 기록·공지·행사장 지도)의 개수를 보여 주는 확인 모달이 뜬다. 확인하면 진행자 기기가 하위 문서를 전부 지운 뒤 방 문서를 지운다. 서버 함수가 없어서(Spark) Firestore가 하위 컬렉션을 같이 지워 주지 않기 때문이다.

## 1. 왜 지금까지 없었나

대기실을 처음 만들 때 "방 삭제는 이후 단계 스펙"으로 미루고 rules에서 막아 두었다(`docs/qa/waiting-room.md` 알려진 한계 3). 하위 컬렉션이 남으면 두 가지가 생긴다.

1. 킬샷 사진(데이터 URL)이 그대로 남는다.
2. 같은 코드로 새 방이 만들어지면(4자 코드, `createRoom`은 방 문서만 검사한다) 옛 참가자·킬샷·원장을 그대로 물려받는다.

그래서 방 문서만 지우는 방식은 쓰지 않는다.

## 2. 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 누가 | 방을 만든 진행자만 | 방 데이터의 주인. 다른 사람은 목록에 그 방이 없다 |
| 2 | 어디서 | 입장 화면 `내가 만든 방` 시트의 방 행 오른쪽 삭제 버튼 | 방 목록이 있는 유일한 곳. 방이 1개여도 지울 수 있게 시트 버튼을 방 1개부터 보인다 |
| 3 | 확인 | 확인 모달에 지워질 것의 개수를 보여 준다. 개수를 읽기 전에는 삭제 버튼을 누를 수 없다 | 사용자 요구 |
| 4 | 진행 중인 방 | 지울 수 있다. 모달에 "게임이 진행 중"이라고 알리고, 지우는 첫 단계가 게임을 끝낸다 | 진행 중으로 남은 지난 방(진행자가 창을 닫은 방)이 흔하다(`docs/qa/waiting-room.md` D-07). 먼저 들어가서 종료하라고 하면 두 단계가 된다 |
| 5 | 순서 | ① 방 닫기(`deleting` 표식 + 대기로 되돌림 + 라운드 지움) → ② 킬샷 · 라운드 원장 · 공지 · 지도 → ③ 참가자 + 방 문서를 한 배치로 | 방 문서가 마지막이어야 중간에 실패해도 목록에 남아 다시 지울 수 있다. 참가자와 방을 한 배치로 지워야 대기실 참가자가 "내보냈어요"가 아니라 "방을 찾을 수 없어요"로 바로 간다 |
| 6 | 하위 문서 목록 | Firestore REST `runQuery` 에 `select: __name__` 을 줘서 문서 이름만 받는다 | 웹 SDK에는 필드 선택이 없어 `getDocs`로 읽으면 킬샷 사진(문서당 최대 900,000자)과 지도(1,000,000자)를 전부 내려받는다 |
| 7 | 개수 | `getCountFromServer`(집계) | 문서를 내려받지 않는다 |
| 8 | 실패 | 모달을 닫지 않고 실패 문구를 보인 뒤 다시 누를 수 있게 둔다. 이미 지운 것은 그대로 두고, 다시 누르면 남은 것부터 이어서 지운다 | 게임 종료 실패와 같은 원칙(눌렀는데 창만 닫히는 모습 방지) |

## 4. firestore.rules

- `rooms` update 갈래 5(방 닫기): 호스트 · 바뀐 키가 `status`·`round`·`deleting` 뿐 · `deleting == true` · `status == 'waiting'` · `round` 없음. 방 상태와 무관(대기·진행 모두).
- `rooms` delete: 호스트 · `deleting == true`.
- 하위 문서 delete(`submissions`·`rounds`·`notices`·`assets`): 호스트 · 방에 `deleting == true`(`isDeletingRoomHost`). 삭제 흐름 밖에서 원장·킬샷을 지울 길을 열지 않는다.
- `participants` delete: 기존 강퇴 갈래(호스트 · 대기 중)에 `|| deleting == true` 를 더한다.
- `participants` create: 방에 `deleting` 표식이 있으면 거부 — 지우는 동안 새로 들어온 참가자가 고아 문서로 남지 않게.

⚠️ **rules를 먼저 배포한다.** 앱만 먼저 나가면 삭제가 첫 단계(방 닫기)에서 전부 거부된다(데이터는 그대로라 손실은 없다). 구버전 앱은 새 갈래를 쓰지 않으므로 rules 선배포가 기존 흐름을 깨지 않는다.

## 5. 엣지 케이스

1. **지우는 중 실패** — 방이 `deleting` 표식을 단 채 남는다. 목록에 그대로 있고, 다시 지우면 남은 것만 지운다. 표식이 남은 방은 새 참가자를 받지 않는다.
2. **대기실에 있던 참가자** — 방 문서가 사라지면 기존 처리대로 `방을 찾을 수 없어요` 화면으로 간다.
3. **콕핏·라운드 운영에 있던 사람(진행 중인 방)** — 방 닫기가 방을 대기로 되돌리므로 기존 전이대로 대기실로 돌아간 뒤, 방이 사라지면 2와 같다.
4. **진행자의 다른 기기** — 그 기기가 열어 둔 화면도 2·3과 같다.
5. **같은 코드 재사용** — 하위 문서까지 지웠으므로 새 방은 빈 상태로 시작한다.
