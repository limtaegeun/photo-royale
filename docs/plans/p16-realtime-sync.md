## 2. 재현 환경

- 실서비스 데이터는 쓰지 않았다. 앱은 로컬 dev 로 띄우고 백엔드는 Firebase 에뮬레이터를 썼다. `firebase.ts` 는 변환 단계에서만 에뮬레이터로 돌렸고 저장소 코드는 그대로다.
- 브라우저와 에뮬레이터 사이에 TCP 프록시를 두어 소켓을 끊김 신호 없이 죽이거나(기지국 이동, 화면 잠금 복귀), 전 구간을 침묵시키거나(음영), 속도를 줄였다(1Mbps, 왕복 300ms).
- 실제 서버는 가입 화면과 같은 익명 공개 읽기(`nicknames/` 의 없는 키)만 했다. 쓰기는 없다.
- iOS 는 시뮬레이터(iOS 26.5 Safari)로 봤다. 실제 iPhone 과 통신망은 확인하지 못했다.

## 3. 원인 1: Safari 가 스트리밍 응답을 묶어 둔다

Firestore 기본 전송은 응답 연결을 열어 둔 채 데이터를 흘린다. Safari 엔진은 이미 도착한 응답을 다음 바이트가 올 때까지 페이지에 넘기지 않을 때가 있다. 다음 바이트는 약 30초 간격의 서버 신호이므로 읽기와 스냅샷이 그만큼 멈춘다.

요청 기록으로 확인했다. 서버는 0.55초에 두 번째 읽기를 받았고 페이지는 30.54초에 결과를 받았다. 멈춤은 간헐적이어서 현장에서 일부 폰에만 나타난다.

| 환경(실서버 읽기) | 기본 전송 | long polling |
|---|---|---|
| iPhone 시뮬레이터, 처음 여는 폰 | 3회 중 3회 멈춤, 읽기 18번 중 9번이 30초 | 5회 중 0회, 읽기 32번 |
| iPhone 시뮬레이터, 이미 쓰던 폰 | 8회 중 1회 멈춤, 읽기 64번 중 3번이 30초 | 8회 중 0회, 읽기 64번 |
| macOS Safari 27.2 | `62 30072 38 25` | `110 148 62 65` |
| Chromium, Firefox | 멈춤 없음 | 멈춤 없음 |

앱에서 게스트 입장은 방 읽기 뒤에 프로필을 읽는다(`getRoom` 다음 `fetchMyGender`). 두 번째 읽기가 멈추면 `대기실에 입장하는 중…`이 그대로 남는다. 호스트는 프로필을 읽지 않아 잘 멈추지 않는다.

앱 전체 흐름으로 잰 수정 전후는 아래와 같다(Playwright WebKit, 에뮬레이터, 게스트 3명).

| 측정 | 수정 전 | 수정 후 |
|---|---|---|
| 게스트 입장 | 30.4 ~ 30.5초 | 0.4 ~ 0.7초 |
| 입장 6초 뒤 호스트 명단 | 0명 | 3명 |
| 공지 수신 12건 | 2건이 30초 | 전부 0.29초 이내 |

### 결정

`experimentalForceLongPolling: true` 로 고정한다. Firebase 문서가 안내하는 공개 설정이고, 응답마다 연결을 닫으므로 묶일 응답이 없다.

- SDK 기본값인 자동 감지는 쓰지 않는다. 첫 응답만 보고 '문제없음'으로 판정해 이 경우를 잡지 못한다(`detected no buffering proxy` 로그 뒤에 멈췄다).
- Safari 만 골라 적용하지 않는다. iOS 의 크롬과 인앱 브라우저도 같은 엔진이라 UA 로 가리기 어렵다.
- 비용은 재 보니 작다. Chromium 공지 수신은 406ms 와 413ms, 실서버 읽기는 양쪽 모두 수십에서 수백 ms 다.
- SDK 가 이 설정을 없애면 다시 검토한다. 문서는 "may be removed in a future release" 라고 적는다.

### 한계

- 이 변경은 연결이 조용히 죽었을 때의 복구를 빠르게 하지 않는다. 항목 3이 맡는다.
- 저속 폰에서 큰 문서가 막는 문제도 남는다. 항목 5가 맡는다.

## 4. 원인 2~4: 남은 항목의 근거

| 원인 | 재현 | 수치 |
|---|---|---|
| 조용히 죽은 연결 | 콕핏에서 소켓을 끊김 신호 없이 죽이고 공지를 보낸다 | 32 ~ 42초 뒤 도착. 앱이 `disableNetwork` 와 `enableNetwork` 를 부르면 0.4초 |
| 음영 뒤 긴 재시도 | 60초 음영 중에 입장한다 | 신호 복구 뒤에도 입장 화면이 남아 전체 185초 |
| 캐시 오판 | 음영에서 콕핏을 새로고침한다 | 10초 뒤 '방을 찾을 수 없어요'로 첫 화면, 복귀 없음 |
| 큰 문서 | 1Mbps 폰, 지도 1MB | 배정 반영 15초(지도 없으면 0.9초), long polling 에서도 9초 |

long polling 은 조용히 죽은 연결의 복구 시간을 줄이지 못한다(`timeoutSeconds` 5, 10, 30 모두 약 32초). 그래서 항목 3이 따로 필요하다.

## 5. 항목 2: 캐시의 '문서 없음'

SDK 는 첫 응답을 받기 전에 오프라인이 되면 빈 캐시로 '문서 없음' 스냅샷을 알린다. `subscribeToRoom` 이 이것을 방 삭제로 전달해서, 음영에서 콕핏을 새로고침하면 10초 뒤 첫 화면으로 쫓겨나고 돌아오지 않았다.

- 부재는 서버가 확인했을 때만 전달한다(`metadata.fromCache` 가 false).
- 서버의 '없음' 확인은 데이터가 같은 메타데이터 변경이라 `includeMetadataChanges` 를 켜야 받는다.
- 그 옵션으로 늘어나는 스냅샷은 같은 내용이면 걸러서 화면이 받는 횟수를 그대로 둔다.

## 6. 항목 3: 죽은 연결을 앱이 다시 연다

끊김 신호 없이 죽은 연결은 SDK 가 스스로 알아챌 때까지 32 ~ 42초가 걸린다. 앱이 `disableNetwork` 뒤 `enableNetwork` 를 부르면 0.4초에 살아난다. 그래서 대기실, 라운드 운영, 콕핏에서 연결을 감시한다(`useFirestoreWatchdog`).

| 측정 | 수정 전 | 수정 후 |
|---|---|---|
| 화면 잠금 뒤 깨우면 공지가 보일 때까지 | 33초 | 0.1초 |
| 연결이 조용히 죽은 뒤 공지 수신 | 41.5초 | 11.5초 |
| 20초 음영 뒤 공지 수신(복구 시점부터) | 21.6초 | 7.6초 |

### 결정

- 3초 넘게 가려졌다 돌아오면 바로 새로 연다. 화면 잠금과 앱 전환 뒤의 연결은 죽어 있기 쉽다.
- 화면이 보이는 동안 15초마다 없는 문서 하나를 읽어 응답을 확인하고, 6초 안에 답이 없으면 새로 연다. 알아채기까지 최대 21초다.
- 읽기 비용: 점검마다 1회, 분당 4회다. 20명이 3시간 쓰면 14,400회이고 Spark 무료 한도는 하루 50,000회다.
- 실패가 이어지면 5, 10, 20, 30초로 간격을 늘린다. 큰 문서를 받는 느린 폰이 연결을 새로 열 때마다 처음부터 다시 받지 않게 하려는 것이다.
- 점검 문서는 `nicknames/__connection_probe__` 다. rules 가 get 을 누구에게나 열고, 밑줄이 닉네임 규칙에 맞지 않아 가입으로 생기지 않는다.

### 한계

- 저속 폰에서 큰 문서를 받는 동안에는 점검이 실패해 연결을 새로 열 수 있다. 1Mbps 폰에서 50초에 3번 나왔다. 항목 5에서 지도를 빼면 줄어든다.
- 점검은 첫 응답을 기다리는 `getDoc` 도 끊을 수 있다. 입장 흐름의 재시도는 항목 4가 맡는다.

## 7. 항목 4: 입장이 끝없이 돌지 않게 한다

`enter()` 는 방 읽기, 프로필 읽기, 참가 등록을 기다리는데 어느 것에도 시간 제한이 없었다. 연결이 멎으면 `대기실에 입장하는 중…`이 언제까지고 남고, 사용자가 할 수 있는 일은 새로고침뿐이었다.

| 측정 | P16 전 | 수정 후 |
|---|---|---|
| 연결이 조용히 죽은 뒤 입장 | 43.6초 | 9.1초 |
| 60초 음영에서 입장 | 185초 동안 입장하는 중 | 26초 뒤 실패 안내와 다시 시도 |
| 신호 복구 뒤 다시 시도 | 없음 | 3초 안에 입장 |

### 결정

- 단계마다 8초를 기다리고, 넘기면 연결을 새로 연 뒤 처음부터 다시 한다. 세 번 해도 안 되면 실패 안내를 띄운다.
- 재시도는 연결 실패(시간 초과, `unavailable`, `deadline-exceeded`)에만 한다. 권한 거부는 반복해도 같다.
- 프로필을 연결 때문에 못 읽었으면 시도가 남아 있는 동안 빈 성별로 등록하지 않는다. 참가 문서에 한 번 쓴 성별은 고치지 않아서 팀 배정에 그대로 남는다.
- 참가 등록은 멱등이라 늦게 끝난 앞선 시도와 겹쳐도 문서는 하나다(재 보니 2명에 문서 2개).
- 실패 안내에 `다시 시도` 버튼을 둔다. 코드를 다시 넣지 않고 같은 방으로 들어간다. 기획 문구가 아니라 이번에 정한 문구다.
- 대기실과 라운드 운영의 구독에 오류 처리를 더한다. 오류로 끝난 구독은 SDK 가 살리지 않아, 화면에 마지막 스냅샷만 남은 채 갱신이 멈췄다.
- 첫 화면의 방 만들기와 코드 확인도 10초로 제한한다. 시간 초과면 다음 시도를 위해 연결을 새로 연다.
